# 架构设想：用 Flutter 生命周期驱动渲染（替代 mini-react）

> 状态：**设想存根，未实现，待验证后再决策**
> 记录时间：2026-10-22
> 相关：`TODO.md` §2.4 暂缓项；现行实现见 `docs/项目架构文档.md`、`packages/hot_patch/lib/src/js_ui/js/mini_react_js.dart`

## 1. 动机

现行架构有两套协调器：

1. JS 侧 mini-react 负责 `mount / patch / unmount`，重建后 diff 出 patch ops；
2. 宿主侧 Flutter element tree 再按结点 id 建真实 Widget。

问题：懒加载需要在 mini-react 里单独发明协议（懒槽位、零尺寸占位结点、`__lazyFn`、`propsChildAt` 重连），
因为 JS 侧不知道 Flutter 何时真正 inflate 某个 element。

设想：**删掉 mini-react 的协调职责**，把“何时构建”交给 Flutter 生命周期本身：

- `JsUiWidget`（组件边界）在 `initState` 里同步调用对应 JS 组件的 `build()`，拿到描述后 `setState` 渲染；
- 描述里的子组件在自己 element inflate 时再调各自的 JS `build()`，逐层递归；
- JS 调 `setState` 时只触发自己那个边界 Widget 的 `setState`；
- 协调发展器只剩 Flutter 一套。

预期收益：懒加载天然成立（Flutter 不 inflate 就不 build），不再需要占位结点/懒槽位那套协议；代码量显著减少。

## 2. 协议草案

### 2.1 JS 侧

组件类保持现状（构造即实例、`props` / `setState` / 生命周期方法不变），删除 element 树与 mount/patch。

新增最小运行时：

```js
// 组件实例登记（id → instance），用于父级引用与 dispose
function __regComponent(inst) { ...; return inst.__id; }

// 边界 Widget 首次 inflate 时调用：只构建自己这一层，不递归构建子组件
function __buildComponent(id) {
  var inst = __components[id];
  var out = inst.build();               // 产出描述树
  return JSON.stringify(__describe(out)); // 只序列化本层 + 内建子树
}

// 子组件在内建描述里以边界标记出现，不展开
// { t: '__component', id: 'c12', props: {...} }
```

### 2.2 Dart 侧

```dart
// 每个 JS 组件实例对应一个宿主边界 Widget（key = JS 实例 id）
class JsComponentNode extends StatefulWidget { ... }

class _JsComponentNodeState extends State<JsComponentNode> {
  Map<String, dynamic>? _desc;

  @override
  void initState() {
    super.initState();
    _desc = _manager.buildComponent(widget.jsId); // 同步 evaluate
  }

  @override
  void didUpdateWidget(old) {
    // props 变化：下发给 JS，再重新 build 本层
    _manager.updateProps(widget.jsId, widget.props);
    _desc = _manager.buildComponent(widget.jsId);
  }

  @override
  Widget build(BuildContext context) => _desc == null
      ? const SizedBox.shrink()
      : DesktopFromDesc.build(_desc!, context); // 内建类型 → 真实 Widget
}
```

关键点：
- 内建类型（Container / Text / Column / ListView…）直接由描述转真实 Widget，**不再有 node id / propsChildIds**；
- 内建子树里的 `{t:'__component'}` 转成 `JsComponentNode`，Flutter 负责它的 element 生命周期与复用；
- JS `setState` → 通过 id → 边界 State 弱引用表调用 `setState`，重跑本层 `build`。

## 3. 成本模型（评估结论）

“复杂页面导致 initState 频繁调 JS build”的担心不成立：`initState` 每个 element 一生只跑一次。
真正的成本是 **setState 沿组件树向下传播**：受影响子树里每个 JS 组件边界各一次跨语言调用。

| 项 | 现状（mini-react） | 设想方案 |
|---|---|---|
| 首次挂载 | 1 次 `evaluate` + 1 条 `jsuiCommit`（ops 批量） | N 个组件边界 = N 次 `evaluate` + N 次 JSON 编解码 |
| setState | JS diff，只下发变化 props | 每个受影响组件重跑 build，整棵内建子树重新实例化为 Widget |
| 协调器 | JS 一套 + Flutter 一套 | 只用 Flutter 一套 |

量级估计（flutter_js 是同步 FFI，单次 `evaluate` + JSON 约 0.05–0.3ms）：
- 首次挂载：30 个边界 ≈ 5–10ms（可接受）；200 个边界 ≈ 30–60ms（掉帧）。
- 高频 setState（手势 / 动画 / 输入）：每次都要序列化整棵子树描述并重建 Widget（Flutter diff 只复用 element，不省 widget 分配），比增量 patch 慢一个量级。
- 列表反而更好：只 inflate 可见项。

结论：**性能不是首要阻塞项，但要靠“组件边界数量可控 + 高频更新下沉到 Dart 能力桥”兜底。**

## 4. 风险清单

| # | 风险 | 说明 / 处理方向 |
|---|---|---|
| R1 | JS 实例与 element 生命周期绑定 | element 因 type/key/位置变化被重建时，JS 实例是否重建？需 `id → State` 弱引用表 + dispose 后回调安全 |
| R2 | 失去帧级批处理 | `initState` 必须同步返回 Widget，不能把 build 延后到帧末；N 个边界即 N 次调用，无合并点 |
| R3 | 能力桥全面重接 | `propsChildIds` / 懒槽位 / `propsChildAt` 会消失；controller / provider / key / 滚动等 capabilities 依赖结点语义，需逐个改到“边界 Widget”语义 |
| R4 | build 中 setState | JS 在 `build()` 内调 `setState`（合法写法）需转成 post-frame 重建，否则 Flutter 报 “setState during build” |
| R5 | 描述序列化膨胀 | 每次 build 输出整棵内建子树，大表单/长文本的 JSON 体积与解析成本需实测 |
| R6 | 迁移回归面 | 现有 demo（AppShell / 首页 / 列表 / 详情 / Provider / PageView / TestWidget）全部依赖现行协议，需整体回归 |

## 5. 下一步：对照实验（验证数据后再决策）

只做测量、不动主干。建议范围：`AppShell + 首页`（含一个约 50 结点的列表）。

1. **单次往返基准**：在同一 flutter_js 实例上空跑 `evaluate("__noop()")` 与一次真实 `build` 描述序列化，各 1000 次取均值/分位。
2. **首次挂载对比**：现方案 vs 原型方案的 `Stopwatch` 总耗时、`evaluate` 调用次数。
3. **典型 setState 对比**：点击一次按钮触发根组件 setState，测总耗时（JS diff + patch vs N 次 build）。
4. **列表滚动**：连续滚动 60 帧，测每帧 build 次数与帧耗时。

决策门槛（建议值，可调）：
- 首次挂载增量 ≤ 30% 且绝对值 ≤ 16ms；
- 单次 setState ≤ 8ms；
- 滚动无持续掉帧；
- 能力桥迁移工作量可接受（R3 评估）。

若达标 → 全量替换；若不达标 → 保留 mini-react，仅把“懒加载”维持在现协议的懒槽位实现上。

## 6. 当前结论与前置说明

- **不要为了懒加载做这次重写**：`TabBarView` / `PageView` 的 `initState` 懒加载已由懒槽位 + 稳定占位结点实现（2026-10-22 已在 macOS 验证：仅首页 `initState` 执行，切 tab / 翻页才挂载对应子页）。
- 本次重写的价值是**去掉双协调器、长期降低复杂度**，属于架构级改动，应单独立项，先实验后决策。
- 实施时若保留 mini-react 的 scheduler 思路（一次 commit 批量 ops），就失去了本设想的“少一套协调器”收益 —— 两者需明确取舍，避免变成两套混杂。

## 7. 待确认问题

- 热更新（整包替换）时，已 inflate 的边界 element 如何强制重建并绑定新实例？
