00 / What & Why

它解决的不是“动态 UI”，而是线上修复

面向「线上出 bug → 运行时切到 JS 补丁修复，无需发版」的场景。组件不需要做任何改造，注解只是构建期元数据；只有在需要热修复时，运行时才加载它的 JS 版本。

编译期：源码级翻译

用 analyzer 静态解析 Dart，把类、方法、build 树一比一翻译成 JS。产物与 lib/ 路径镜像，读 JS 等于读 Dart；禁止手改产物。

运行期：JS 逻辑闭环

setState、provider、订阅与重建全部发生在 JS 侧，最终归约为增量 patch ops。宿主不理解任何状态语义。

渲染：Flutter 只组装

宿主只做两件事：把 JS 结点 type 映射成真实 widget，并应用增量补丁。原生与热更版本共用同一套属性协议。

01 / Getting started

四步接入，组件零改造

接入只需要依赖、注解、构建、加载四步。被标注的类始终是普通 Flutter widget，在未加载补丁的地方照常原生渲染。

适用 已有 Flutter App 改动 组件加注解 · 启动处注册 不改造 业务逻辑 / 状态管理 / 布局 产物 patch/ 与 lib/ 路径镜像

Step 01 · 添加依赖

运行时与注解进 dependencies，生成器与 build_runner 只进 dev_dependencies。

dependencies:
  hot_patch_annotations: ^0.1.5   # 注解
  hot_patch: ^0.4.0               # 运行时（JS 运行时 + 宿主渲染 + 能力桥）

dev_dependencies:
  hot_patch_generator: ^0.13.0   # 编译期翻译（不进入包体）
  build_runner: ^2.4.13

Step 02 · 给组件打注解

@PatchEntry 的收集口径是整个 widget：非 static 字段 → JS 状态；除 build / 生命周期外的方法 → JS 方法；build() → JS 渲染入口。没有字段级或方法级标注。

import 'package:flutter/material.dart';
import 'package:hot_patch_annotations/hot_patch_annotations.dart';

@PatchEntry('Counter')
class Counter extends StatefulWidget {
  const Counter({super.key});

  @override
  State<Counter> createState() => _CounterState();
}

class _CounterState extends State<Counter> {
  int _count = 0;                                  // → JS 实例状态
  void _inc() => setState(() => _count++);          // → JS 方法

  @override
  Widget build(BuildContext context) => Column(
        children: [
          Text('count = $_count'),                        // 插值原样保留
          ElevatedButton(onPressed: _inc, child: const Text('+1')),
        ],
      );
}

Step 04 · 声明资源并加载

Flutter 的目录 asset 声明不递归，需要逐目录或逐文件列出。加载时组件名通过 ?component= 传入，运行时会在请求前剥离 query。

flutter:
  assets:
    - patch/components/
    - patch/flutter.js
    - patch/runtime.js
    - patch/manifest.json
JsUiWidget(
  jsAsset: 'assets/patch/components/counter.js'
           '?component=Counter',
)
三个容易踩的坑

assets: 声明不递归；?component= 必填，且必须与入口模块注册的类名一致；同一进程内所有 JsUiWidget 应指向同一补丁包身份，混用不同版本会触发明确报错而不是反复切换。

让 JS 调用原生能力

网络、路由、WebView、原生 SDK 等只能由宿主执行的能力，用 @HostInjected 标注静态方法或顶层函数。类照常翻译，只有方法体换成通道调用，调用点与 Dart 一比一。

class HostGreeter {
  @HostInjected()
  static String greet(String name) => 'Hi, $name';
}

void main() {
  registerHostMethods();   // 扫描注解生成的注册清单，一次注册全部通道
  runApp(const App());
}

通道名默认取方法名；参数载荷按实参形态给（纯位置 → 数组，纯具名 → 对象，混合 → 对象 + "@args"），宿主用 Function.apply 还原 Dart 调用语义。返回值是 Promise，可 await。

02 / Design laws

五条设计定律

它们不是实现细节，而是基座契约。任何新需求、重构、能力扩展都必须先对照这五条；与它们冲突的方案，宁可改业务代码，也不改基座设计。

LAW 01

源码级翻译：Dart 单源，JS 是编译产物

类名、字段名、方法签名、方法体语句、build 树在 JS 侧保持 Dart 原貌，读 JS 产物等于读 Dart 源码。翻译器只做语言层映射，不做语义改写、不做优化裁剪。StatefulWidget 的 widget 类与 State 类合并为一个 JS 类，是唯一特例。

LAW 02

宿主注入补全：JS 没有的能力由 Flutter 补

不存在的对象与方法由宿主注入，而不是让翻译器改写调用方。四种形态：能力桥、@HostInjected 通道、JS 内建原型补齐、原生组件注册。禁止在生成器里按方法名做映射改写。

LAW 03

逻辑全在 JS 端：JS 是唯一事实源

setState、provider、任何状态库的状态与重建都发生在 JS 侧的 mini-react 里，最终归约为「JS 重建子树 → 产出增量 patch ops → jsuiCommit 下发 → 宿主应用」。

LAW 04

Flutter 侧只组装 widget tree

宿主只做两件事：把 JS 结点的 type 映射成真实 Flutter widget（JsWidgetRegistry），以及应用 JS 算好的增量补丁（JsUiStore）。新增 JS 组件、新增状态库都不改宿主代码。

LAW 05

Flutter 生命周期驱动 JS 方法

JsUiWidget 是宿主入口：initState 时准备运行时、注册能力桥、加载并 mount JS 根；dispose 时调用 disposeRoot(pageKey) 统一释放该页关联的句柄、控制器与订阅。JS 组件自身的生命周期（initState / didChangeDependencies / didUpdateWidget / deactivate / dispose）由 mini-react 统一派发，宿主不逐个转发。

定律二落地：四种补全形态

形态场景入口 / 约束
能力桥ScrollController、TabController、GlobalKey、BuildContext 等有真实原生对应物的对象；CustomPainter 的绘制录制重放；Canvas 图片句柄packages/hot_patch/lib/src/js_ui/capabilities/；一个能力一个目录，核心零改动
@HostInjected 通道网络、路由、WebView 等纯宿主方法调用类照常产出 JS 类，被标注方法体改为 _app_host_.invoke(通道名, 载荷)
JS 内建原型补齐Dart 标准库方法在 JS 内建类型上不存在（如 List.clear）运行时同名同义补齐，enumerable:false + 存在性守卫，禁止挂 Object.prototype
原生组件注册JS 无法 / 不应翻译的纯原生 widgetregisterNativeComponent(name, build)，全局一次注册，放在 runApp 之前

稳定性的三条底线

一条语法一个规则

同一语法现象只有一处实现；不存在 per-widget / per-class 的翻译器子类。组件与普通类共用同一条翻译路径。

协议版本化

当前协议（element 形态 __element / __children、patch ops、句柄信封、颜色序列化、lazyChildren）按只增不改维护；必须替换已发布形态时，升主协议版本并给迁移方案。

设计变更即清理

确认 L2 / L3 变更后，旧设计的代码、分支、注册项、配置表项、产物与文档必须在同一次变更内删除。验收标准是「旧设计已不存在」。

为什么强调“不要按名字判断”

生成器不带完整类型解析。若按方法名全局改写，clear() 既是 List.clear() 也是 TextEditingController.clear()，必然撞车。因此翻译判据只来自源码事实：构造签名、extends 链、import 链与文件 / package 归属；唯一例外是「JS 内建同名语义差异」的构建期固定映射表，且只在接收者静态类型可判定时生效。

03 / Layers

分层与职责边界

整个仓库是一个 Dart pub workspace：三个包、一个示例 App、一个本地补丁服务。每层只做自己该做的事，跨层只通过协议与唯一通道交流。

04 / Compile time

编译期：一条路径、五个阶段

翻译器全程使用 analyzer 静态解析，不执行任何 Dart 代码。组件与普通类共用同一个入口，差别只在“是否作为组件产物组装”。

STAGE 01 · 根类收集 先按文件内容分流，再决定产出什么

含 @PatchEntry 的文件是根文件，产出这些组件；否则只产出可导出的普通类（模型 / 单例）；两者都没有（如 main.dart）则不产出。分流与目录结构无关。

STAGE 02 · 依赖发现 沿 import 链做符号级引用扫描

只有真正被可达类引用到的类才产出，未被引用的模型不翻译。@HostInjected 方法的方法体不参与引用扫描（JS 侧只有通道调用），因此只在宿主实现里用到的类型不会被连带翻译。

STAGE 03 · 类模型与语法翻译 收集与翻译共用中立类模型

识别 StatefulWidget 时合并同文件 State 类，是唯一分叉。字段 / 方法 / 控制流 / 表达式走 js_translator.dart 与 dart2js.dart；构造统一渲染为 constructor(args) + __applyProps(args)。

STAGE 04 · build 树翻译 没有 per-widget 实现，只有值形态分派

element_json.dart 是统一入口，value_forms.dart 按值的形态（字面量 / 构造 / 静态工厂 / 常量引用 / 列表 / 闭包）分派，结构化样式的运行时值类见 builders/runtime/js/style_values_js.dart。所有实参按原名进 props。

STAGE 05 · 产物组装 路径镜像 + 依赖 import + 清单 hash

产物与 lib/ 路径一一对应；flutter.js 生成 Component 基类、宿主包装类与值类；最后 ui_patch_manifest 用 findAssets('patch/**.js') 列出全部 JS 并逐个算 hash。

同一份源码，两种形态

下面是形态示意（节选，非逐字产物）：类名、字段名、方法名、build 树结构保持 Dart 原貌；构造统一收一个 args 对象。

@PatchEntry('Counter')
class Counter extends StatefulWidget {
  const Counter({super.key});

  @override
  State<Counter> createState() => _CounterState();
}

class _CounterState extends State<Counter> {
  int _count = 0;
  void _inc() => setState(() => _count++);

  @override
  Widget build(BuildContext context) => Column(
        children: [
          Text('count = $_count'),
          ElevatedButton(onPressed: _inc, child: const Text('+1')),
        ],
      );
}
export class Counter extends StatefulWidget {
  constructor(args) {
    super(args);
    this._count = 0;
  }
  _inc() {
    this.setState(() => {
      this._count += 1;
    });
  }
  build(context) {
    return new Column({
      "children": [
        new Text({
          "data": "count = " + this._count
        }),
        new ElevatedButton({
          "onPressed": () => this._inc(),
          "child": new Text({ "data": "+1" })
        })
      ]
    });
  }
}

产物中还会保留 Dart 的插值、三元、集合展开、类型实参等；上面只展示主干形态。

五条翻译约束

主题规则
构造翻译A(args) → new A({...})，A.b(args) → A.b({...})；位置实参由源码构造签名映射为形参名。未知签名 → 构建期告警并丢弃，不生成下标键或占位兜底。
属性原样下发Dart 构造实参按原名进 props。child / children / slivers / tabs 都是普通具名实参，禁止特殊判断。
命名构造 / 静态工厂一比一发射为 X.b({...})；JS 侧由同名静态方法把构造名写进 props.factory，宿主只按 factory 选原生工厂。
builder 形态只认显式协议：命名构造由代理类展开到 children.__items；delegate 形态是 {__delegate:'builder', builder, childCount}。不得按类型名白名单或属性名猜测。
泛型类型擦除；<T,...> 译为 typeArguments 元信息，随构造 props 或调用尾参对象下发。不生成运行时代码，不做 per-type 分支。
无静默原则

翻译失败、未覆盖语法、无法识别的引用都必须输出构建期告警，禁止静默丢弃或降级。产物里的占位结点是诊断兜底，不是长期方案。

05 / Runtime

运行时：JS 侧的闭环

宿主从不主动询问 JS 状态，JS 也从不直接触碰 Flutter widget。两端只交换序列化的 patch 与事件；状态变化终点永远是 JS 下发的 patch。

帧合并的调度

setState 只标脏，宿主在每帧 begin frame 调用 __jsui.flushPending() 统一重建。同一帧内来多少次 setState（如滚动通知逐条回传）都只 build 一次，与 Flutter 的调度粒度一致。

数据共享也在 JS 内闭环

InheritedWidget 与 ChangeNotifierProvider 都没有宿主 renderer。节点用 __inheritedElements 声明作用域，依赖登记在 __dependencies / __dependents；提供者变更时标脏依赖者，先 didChangeDependencies 再 build。

已挂载项照常 didUpdateWidget

父级每次重建都会把新元素 patch 到已挂载子树，组件照常 didUpdateWidget → build，与原生一致。只有元素引用相同（const 站点缓存）才按 el === oldInst.__el 短路。

懒槽位与宿主 element 同寿

宿主 inflate → lazyMount；滚出缓存 / 切走 Tab / 整页退出 → lazyUnmount。item 的 State 会被销毁，滚回来是新实例——与 Flutter 原生一致。跨滚动保留的数据应放父组件或模型层。

句柄模型：真实对象只在一端

Controller、函数、Key、Painter 都是同一种东西的不同 kind。拥有端持有真实对象，另一端只持有 id，所有操作按 id 转发；通用层提供 create / call / set / release 等 op，新能力只需注册自己的 kind 描述符。

归属与释放

  • 构造期、initState、build、事件执行期创建的句柄，记到该组件实例的 __owns。
  • 组件从树上摘除时整份释放，与 Dart State.dispose 对齐。
  • 无组件归属的随页面释放，disposeRoot 兜底。
  • 全局 handles 是 id → 对象的唯一反查表。

唯一出口与唯一入口

  • JS → 宿主：只有 _app_host_.invoke(channel, args)。
  • 宿主侧：只有 JsRuntimeManager.registerHostMethod。
  • 增量补丁 jsuiCommit、日志、@HostInjected 全部复用这一个入口。
  • 禁止新开平行通道或恢复已删除的冗余注册入口。

补丁身份与版本切换

运行时是全局唯一的。补丁包身份版本由 manifest 的 version + buildTime + protocol 组成，写入 JsRuntimeManager 内存；版本不一致即整体失效模块与运行时，只认版本差异，不因重复下载反复失效。

STEP 01 加载新包

asset、远程 zip 或已加载模块完成加载；身份版本与当前内存不一致时，清空已加载模块并重新求值 runtime.js。

STEP 02 活跃页登记

所有仍 mounted 的 JsUiWidget 进入待重载集合（含 Navigator 栈下方离屏路由、同屏多实例）。判断由独立的 JsRuntimeSwitchCoordinator 维护，不扫 Navigator / Element 树。

STEP 03 可见页确认，离屏页静默

可见页弹一次原生 dialog；确认后全部执行页面级重载（重建 JsUiStore 与 JS root，保留 Flutter 路由与页面本身）。离屏页不弹窗，直接静默重载。

STEP 04 只加载当前身份版本

自动重载只加载当前运行时身份版本的产物；若某页补丁源版本不一致，明确报错，避免 A/B 页面来回切换。

两个边界

同一进程内所有 JsUiWidget 必须指向同一补丁包身份；混用不同 zip / 不同批次会明确报错。命令式弹层的独立 root 目前不在活跃页注册表内，版本切换时若仍有弹层打开，弹层内容会随旧运行时失效。

为什么 MediaQuery 需要缓存

已接入的三方库：provider flutter_easy_refresh cached_network_image。其中 provider 是纯 JS 结点（无宿主 renderer），EasyRefresh 与 CachedNetworkImage 是宿主组件。

懒加载的运行时协议

构建期

  • lazyChildHostTypes 是唯一事实源，构建期生成包装类的 static __lazy 或 Component.host 的 lazyRule
  • 包装类 / Component.host 按构建期规则，在构造期打 lazyChildren: true
  • 新增 / 调整懒容器 = 改这一处配置 + 重出产物

运行时

  • 只认元素标记，不认识类型
  • 协议：children.__builder / __items / delegate；占位 props 的 __lazy / __lazyFn / __keepAlive
  • 宿主 inflate → lazyMount；dispose → lazyUnmount

保活与更新语义

  • 保活：子树中任意组件声明 wantKeepAlive，JS 在挂载、父级重建、组件自身重建后把声明经 __keepAlive 下发；宿主注册真实 KeepAlive，切走 Tab 不再销毁 element。保活只看子树，不越过嵌套懒槽位。
  • 父级重建：已挂载项照常 didUpdateWidget，与原生一致；只有 const 元素引用相同才短路。不要按「props 值相等就跳过 patch」，那会吞掉 didUpdateWidget 里的副作用。
  • 帧合并：setState 只标脏，宿主每帧统一 flush；didUpdateWidget 次数 ≈ 帧数，而不是通知数。
  • 性能建议：props 里不要放每次新建的不可比对象（随机 id / 时间戳 / 裸函数实例）；需要强制刷新时把变化体现在产出里（如 salt / version）。

01 · 补丁分发与版本切换

三种源 · 一个身份

JsUiWidget.jsAsset 支持三种补丁源，加载后走同一套模块求值与身份版本逻辑。

补丁源形式说明 / 约束
随包资源assets/patch/...目录 asset 声明不递归，需逐目录 / 逐文件声明
远程补丁包http(s)://host/patch.zip?component=Name&entry=path/to.js下载解压后与 asset 同一加载逻辑；component 必填，entry 可选（不传按 component 反查）
已加载模块同一 JS 运行时里的其它模块路径模块注册表 __modules 是运行时全局的，模块只求值一次
 
JsUiWidget(
  // query 会被剥离；component 必须与入口模块注册的类名一致
  jsAsset: 'http://127.0.0.1:8765/patch/patch.zip'
           '?component=HelloCard&entry=components/hello_component.js',
  props: const {'title': 'Hot patch'},
  showBuildTime: true,  // 右上角显示补丁打包时间，不参与命中测试
)

manifest：补丁的身份证

字段作用
name / version业务信息，可被 build.yaml 的 ui_patch_manifest 选项覆盖
protocol产物协议版本，取自生成器包版本；运行时拒绝主版本不匹配的包
buildTime打包时间；身份版本的一部分，也用于调试角标
resources每个 JS 资源的内容 hash；用于完整性校验与缓存

身份版本与页面级重载

身份版本 = version + buildTime + protocol（任一字段变化都视为另一个包）。同进程内后续加载的包身份与内存不一致时，运行时清空已加载模块并重新求值 runtime.js；随后由活跃页注册表驱动页面级重载（详见 协议、句柄与版本）。

  • 同一进程同一身份：所有 JsUiWidget 必须指向同一补丁包；混用不同版本会明确报错，而不是反复切换运行时。
  • 页面隔离：运行时全局唯一，每个 JsUiWidget 用 pageKey 隔离自己的结点树 / provider / 订阅 / 脏队列；同屏多实例互不影响。
  • 模块表是全局的：任一远程包 fresh 会清空全部页面已加载的模块，因此两个页面不能依赖同一模块路径的不同版本。

02 · 宿主注入与原生组件

唯一出口

JS 只能通过宿主方法触达原生能力；宿主方法只有一个注册入口。另有原生组件注入作为“不翻译也能量”的兜底。

@HostInjected 的边界

主题规则
可用位置静态方法或顶层函数。实例方法不生效（JS 侧 receiver 回不到宿主实例），私有声明跨库不可见
通道名@HostInjected() 缺省取方法名；@HostInjected('name') 显式指定
参数载荷纯位置 → 数组；纯具名 → 对象；混合 → 对象 + "@args" 键装位置实参。宿主用 Function.apply 还原，省略参数走实现默认值
返回值Promise，可 await；宿主抛错则异常抛回 JS 调用者；未注册通道也回填 null，不留悬空 Promise
JS 类形态类照常产出同名 JS 类，被标注方法仍在；但宿主注入类在 JS 里只保留「类 + 被标注的方法」，字段 / 其它方法 / import 不产出
依赖扫描@HostInjected 方法体不参与引用扫描，只在其中用到的类型不会被连带翻译
 
class Network {
  @HostInjected()
  static Future<Map> post({
    required String url,
    dynamic params,
  }) async => {'data': params, 'code': 200};
}

// JS 调用点与 Dart 一比一：
// Network.post(url: u, params: p)
// → Network.post({ "url": u, "params": p })

原生组件注入

标记 @PatchIgnore 的组件，或宿主没有 renderer 的类型，产物会保留具体类型名。业务在 main() 里全局注册一次原生实现即可：

registerNativeComponent(
  '_LabeledDivider',
  (c) => LabeledDivider(
    text: c.str('text') ?? '',
    child: c.children['child'] as Widget?,
  ),
);
  • 回调收到完整 JsRenderContext：props、children slot、invoke；可渲染子组件并把事件回传到 JS。
  • 重复注册同名会覆盖（覆盖时告警），因此必须放在 runApp 之前，不要放进 build()。
  • 值对象（InputDecoration / BottomNavigationBarItem / DropdownMenuItem）不需要注册；它们由父 renderer 就地还原。

框架内建通道

lognativeToastjsuiCommitjsuiEventResult

内建通道在 JsUiWidget 启动时自动注册；业务只需注册自己的 @HostInjected 方法。JsRuntimeManager.navigatorKey 需传入 MaterialApp.navigatorKey，全局级服务（toast / 路由推页）靠它定位 Navigator 与 ScaffoldMessenger。

级别用途典型来源

HotPatchLog.sink = (r) => MyLogPlatform.upload(

变更分级：决定能不能动核心

L1 · 加能力

只走扩展点，核心零改动

默认且首选。新增能力库、注册 renderer、补宿主方法、加原生组件都属于这一级。

L2 · 加语法

新增语法分支或产物模块

既有语法产物不变，协议次版本只做加法；若替换旧实现，旧实现同步删除。

L3 · 改协议 / 老策略

必须先沟通确认

升主协议版本、给兼容或迁移方案、更新架构文档、删除被替换的旧路径。未确认前禁止。

新增一个运行时能力

  1. 在 packages/hot_patch/lib/src/js_ui/capabilities/ 新建目录，写 Dart 桥与 JsUiLibrary 子类。
  2. 在 js_ui_library.dart 的 _seedBuiltins 里加一行注册（外部库则让业务在 main() 调 registerJsUiLibrary）。
  3. JS 片段写进生成器 builders/runtime/js/，随 patch/runtime.js 发布；若只是库自己的 API 面，放该库模块。
  4. 确认 reconciler / JsUiWidget / disposeRoot / 桥 / 句柄注册表零改动。

判据：这段 JS 若不认识任何具体库 / 具体 API 也成立 → runtime.js；否则归它的库模块。

新增一个可翻译的 widget

  1. 先确认翻译路径是否已覆盖：构造实参、值形态、样式、事件、children 拆分都是通用的。
  2. 补宿主 renderer（JsWidgetRegistry 或能力库 registerWidgets），注册 key 必须与产物里的 type 字符串同名。
  3. 若子项组织方式不同（builder / separated / delegate / 懒容器），调整 js_class_defs.dart 的构建期表。
  4. 若涉及新的值对象，在 flutter.js 值类区写普通类（构造 + toJSON），宿主用 c.element(...) 还原嵌套 Widget。
扩展时不要做的事

不要发明手册未登记的产物形态 / 命名 / 辅助函数；不要按类名 / 方法名 / 属性名判断执行；不要对固定子组件属性名做特殊处理；不要静默丢弃或降级；不要手改 patch/ 下的产物；不要新开 JS ↔ 宿主通道；不要为单个功能设计专用 runtime API。

按快速开始跑通示例，观察原生 vs JS 热更的同屏对比。

READ 02看架构

读《项目架构文档》的五条定律与分层，建立边界感。

READ 03看翻译

从 analyze_dart_class → element_json 跟一条 build 树。

READ 04再扩展

按 JsUiLibrary 模板加一个能力，确认核心零改动。
