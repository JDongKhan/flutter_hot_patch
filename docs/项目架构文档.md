# flutter_hot 项目架构文档

> 本文档是项目的**基座契约**：记录核心设计思想、分层职责与不可逾越的设计红线。
> 任何新需求、重构、能力扩展都必须先对照本文档；与本文档冲突的方案，宁可改业务代码也不改基座设计。

---

## 1. 核心设计思想（第一性原理）

本项目由以下五条设计定律构成，优先级高于任何局部实现：

### 定律一：源码级翻译 —— Dart 单源，JS 是编译产物

将 Flutter（Dart）源码**几乎一致地**翻译成 JS 源码。

- 业务代码只有一份真相来源：示例 App 的 `example/lib/` 下的 Dart 源码；`example/patch/` 下的 JS 全部由 `hot_patch_generator` 生成，标注 `GENERATED CODE - DO NOT EDIT`，**禁止手改**。
- 「几乎一致」的含义：类名、字段名、方法签名、方法体语句、build 树结构在 JS 侧保持 Dart 原貌，读 JS 产物等于读 Dart 源码。翻译器只做语言层映射，不做语义改写、不做优化裁剪。
- Dart 侧与 JS 侧方法参数签名完全一致；StatefulWidget 唯一特例是 widget 类与 State 类合并翻译为一个 JS 类。

### 定律二：宿主注入补全 —— JS 没有的能力由 Flutter 侧补

JS 不存在的对象、方法等，由 Flutter（宿主）侧注入补全，而不是让翻译器改写调用方。

四种补全形态，按场景各就各位：

| 形态 | 场景 | 入口 |
|---|---|---|
| 能力桥（capabilities） | ScrollController、TabController、GlobalKey、BuildContext 等有真实原生对应物的对象 | `packages/hot_patch/lib/src/js_ui/capabilities/` |
| `@HostInjected` 通道 | 网络、路由、WebView 等纯宿主方法调用 | 生成器产出 `_app_host_.invoke(通道名, [参数])` 调用 |
| JS 内建原型补齐 | Dart 标准库方法在 JS 内建类型上不存在（如 `List.clear`） | `runtime_source.dart`【1c】节，同名同义补齐到最具体的内建原型 |
| 原生组件注册 | JS 无法/不应翻译的纯原生 widget | `registerNativeComponent(name, build)` 全局一次注册 |

**禁止**在生成器里按方法名做映射改写（生成器不带类型解析，同名方法必撞车）；**禁止**为了绕开 JS 限制而修改 Dart 单源的写法。

### 定律三：逻辑全在 JS 端 —— JS 侧是唯一事实源

JS runtime 加载 JS 后，**所有的逻辑、状态、以及状态变化后的重建逻辑全部在 JS 端执行**。

- setState、provider、任何状态库的状态与重建都发生在 JS 侧的 mini-react 里，最终归约为「JS 重建子树 → 产出增量 patch ops → 经 `jsuiCommit` 下发 → 宿主应用」。
- 宿主（Flutter 侧）**不理解任何状态语义**，只做两件事：
  1. 把 JS 下发的 `type` 映射成真实 Flutter widget（`JsWidgetRegistry`）；
  2. 应用 JS 算好的增量补丁（`JsUiStore`）。
- 因此新增 JS 组件、新增状态库都**不改宿主代码**；只有新增「Flutter 侧不存在的视觉 widget」时才往宿主注册表加一条。

### 定律四：Flutter 侧只组装 widget tree

Flutter 侧在相应时间调用 JS 对象的 `build`，拿到 JS 对象树（element tree），组装成 Flutter widget tree。

- 首次挂载：宿主调 JS 侧 `api.mount(pageKey, ...)` → JS 实例化组件并执行 `build` → mini-react reconciler 展开整棵 element 树 → 下发全量 patch → 宿主递归组装 widget tree。
- 后续更新：JS 侧状态变化触发局部重建，宿主只收到**增量 patch**（add/remove/update），不重新整树组装。
- 宿主侧的渲染协议与「原生 JSON 渲染」共用同一套属性协议：原生版本与 JS 热更版本是同一个组件的两种载体，行为必须一致。

### 定律五：Flutter 生命周期驱动 JS 方法

Flutter 侧利用 StatefulWidget 的生命周期来驱动 JS 侧的方法。

- `JsUiWidget`（StatefulWidget）是 JS-UI 页面的宿主入口：`initState` 时准备运行时、注册能力桥、加载并 mount JS 根；`dispose` 时调 `disposeRoot(pageKey)` 统一释放该页面关联的所有句柄、控制器、订阅。
- JS 组件自身的生命周期（`initState` / `didChangeDependencies` / `didUpdateWidget` / `deactivate` / `dispose`）与 Flutter 对齐，由 JS 侧 mini-react 统一派发，宿主不逐个转发。
- 页面级资源兜底释放只认 `disposeRoot` 一个入口，保证「页面退出 = 该页资源零残留」。

### 2.1 仓库目录布局（pub workspace）

仓库根是一个 Dart **pub workspace** 聚合包（根 `pubspec.yaml` 用 `workspace:` 列出成员，
各成员 pubspec 声明 `resolution: workspace`），全仓共享同一份依赖解析、同一个
`pubspec.lock` 与同一个 `.dart_tool/`：

| 目录 | 角色 |
|---|---|
| `packages/hot_patch_annotations` | 注解定义 |
| `packages/hot_patch_generator` | 编译期翻译与产物组装 |
| `packages/hot_patch` | 运行期 JS 运行时 + 宿主渲染 + 能力桥 |
| `example/` | 示例 App（唯一 Flutter 应用）；业务 Dart 单源在 `example/lib/`，产物在 `example/patch/` |
| `tool/patch_server.dart` + `start_patch_server.sh` | 本地 patch 静态服务，服务于 `example/patch/` |

上图中的「源层 `lib/`」「产物层 `patch/`」物理位置即 `example/lib/`、`example/patch/`。

### 2.2 三个 package 的分工

| Package | 角色 | 关键约束 |
|---|---|---|
| `hot_patch_annotations` | 注解定义（`@PatchEntry` / `@PatchIgnore` / `@HostInjected`） | 纯注解，零逻辑 |
| `hot_patch_generator` | 编译期：Dart → JS 翻译与产物组装 | 不含 flutter_hot 强相关配置；生成器单包，禁止拆多 package |
| `hot_patch` | 运行期：JS 运行时注入 + 宿主渲染 + 能力桥 | 不含业务；不理解状态语义 |

## 3. 核心机制

### 3.1 翻译：单入口、递归、数据驱动

- 翻译器唯一入口为 `analyze_dart_class.dart` 的 `translateClass(...)`；识别到 StatefulWidget 时合并同文件 State 类，是**唯一**分叉。组件与普通类共用同一套字段/方法/依赖/widget 树翻译。
- 依赖发现：仅在扫描到 `@PatchEntry` 注解的根类时启动翻译，沿 import 链做**符号级**引用扫描，真正被引用的类才产出；依赖链遇到 `@HostInjected` 类直接断掉。
- build 树统一渲染为 `__h(type, props)` 元素描述：所有 Dart 实参按原名进 props。元素工厂 `__h` 再按**值形态**拆分——值是元素（`element: true`）或元素数组时，按原名移入 `children`；delegate 描述（`{__delegate: …}`）同样移入 `children`；其余值留在 `props`。拆分**与键名无关**：`child` / `content` / `top` / `actions` / `items` 走同一条路径。JS 组件类（type 是函数）的 props 原样保留，供 `__applyProps` 派生构造字段。
- widget 翻译**没有 per-widget 实现**：`widget_json.dart` 按通用协议（`on*` 事件、`delegate` 子结点提供者、位置实参形参名、`builder / *Builder` 回调命名约定）+ `value_forms.dart` 按值的形态（字面量 / 构造 / 静态工厂 / 常量引用 / 列表 / 闭包）分派，内建与自定义组件同一套规则。翻译侧因此无需 per-widget 实现；但「能被渲染」仍需宿主注册 renderer，产物形态不同时还要调整 `js_widget_defs.dart` 的登记表（见第 5 节）。
- 产物协议：位置实参按 **Flutter 声明的形参名**下发（`Text('hi')` → `{data: 'hi'}`）；未登记形参名的类型遇到位置实参时构建期告警并丢弃，不生成下标键兜底。命名构造 / 静态工厂保留构造名（`{factory: 'separated', itemBuilder: …, separatorBuilder: …}`）。
- **builder 形态只认显式协议**：命名构造 `.builder` / `.separated` 由生成的 JS 代理类展开，结果写入 `children.__items`；`delegate: SliverChildBuilderDelegate(...)` 译为 `children.delegate = {__delegate: 'builder', builder, childCount}`。运行时与宿主 renderer **不得**按类型名白名单或属性名猜测 builder 形态。
- 翻译失败/不可翻译的场景输出**构建期告警**，禁止新增静默丢弃路径。（`try/catch/finally`、`throw`、`assert` 已支持基础翻译；其余未覆盖语句仍会告警后跳过。）

### 3.2 运行与重建：JS 侧闭环

```
JS: setState(fn) → 修改字段 → markDirty(组件)
                      │
                      ▼（批处理 flush）
              重新 build → reconciler diff（eq/keyOf 比对）
                      │
                      ▼ 产出增量 patch ops
        jsuiCommit(pageKey, ops) ──唯一桥──▶ 宿主 JsUiStore 应用 ops
                                                  │
                                                  ▼
                              受影响结点 setState 重建 Flutter 子树
```

宿主从不主动询问 JS 状态；JS 从不直接触碰 Flutter widget。两端只交换**序列化的 patch 与事件**。

### 3.3 事件：构建期锚定，禁止运行时启发

- 事件回调无法跨语言传递，统一登记为**句柄**（kind=fn）。
- 生成器把**所有**事件统一产出构建期**箭头闭包**：`this.__bindFn(位点号, [捕获值], (...a) => …)`。闭包在 build（或抽出的 builder 方法）里创建，天然捕获当时的局部变量 / 循环变量，与 Dart 闭包同语义；句柄绑定到**定义该事件的组件实例**。宿主触发时只回传句柄 id + 参数数组。
- 位点号是**编译期**产物中的稳定编号（同一个 `on*` 位点每次构建都相同），捕获值是闭包引用的构建期局部值（对象 / 函数按引用身份、原始值按 String 比较）。运行时以「位点号 + 捕获值」复用句柄 id：重建后 id 不变（props 稳定、增量补丁生效），循环项捕获到不同值时各自独立（回调不互相覆盖）。**不得**把表达式放进字符串在点击时求值（`new Function` 丢失构建期作用域，引用局部的 `onPressed: () => model.inc()` 会静默失效）。
- **禁止**改为运行时按事件名分发或按树形状猜测归属——那会丢失嵌套组件的事件归属正确性。
- 事件参数必须为 JSON 可序列化类型，非可序列化对象在 renderer 层投影为基础值后再回传。

### 3.4 跨语言句柄模型

- 真实对象仅存在于一端（owner），另一端只持有 id 句柄，所有操作按 id 转发到拥有端。Controller、函数、Key、未来的 Widget 都是同一种东西的不同 kind。
- 句柄 id 格式 `<端>:<种类>#<序号>`；释放语义「拥有端为准 + 组件/页面兜底」。
- **归属**：控制器 / Key 等句柄随**持有它的组件实例**释放——构造期（字段初始化）、initState、build、事件执行期创建的句柄都记到该实例的 `__owns`，组件从树上摘除时整份释放（与 Dart 的 `State.dispose` 对齐）。无组件归属的（静态字段 / 模块级）随页面释放，页面销毁时兜底。
- 归属只决定释放时机：全局 `handles` 仍是 id→对象的唯一反查表（宿主 `invoke(id)` / 组件卸载 / `dispose()` 里都可能没有页面上下文）。
- 新增能力只需在两端注册对应 kind 描述符即可接入，核心文件（桥接、注册表、disposeRoot、生成器）无需改动。

### 3.5 通信：唯一出口

- JS → 宿主方向的唯一出口是 `_app_host_.invoke(channel, args)`（内部统一打到单桥通道，宿主一次订阅、二次分发）；增量补丁 `jsuiCommit`、日志、`@HostInjected` 方法全部复用这一个入口。
- 宿主侧所有宿主方法统一通过 `JsRuntimeManager.registerHostMethod` 注册，禁止新增平行通道、禁止恢复已删除的冗余注册入口。

## 4. 设计红线（防止变味）

以下红线是基座稳定的保障。触碰任一条，即视为破坏架构，必须在评审中驳回：

1. **宿主不感知状态**。宿主代码里出现对 setState/provider/具体状态库语义的理解，即为越界。状态与重建的终点永远是「JS 下发 patch」。
2. **JS 产物只生成不手改**。`patch/` 下一切 JS 由 build_runner 产出；修 bug 改 Dart 单源或生成器，永不改产物。
3. **翻译保真，不改写语义**。生成器不做优化、不裁剪、不按名字映射方法；JS 缺的能力按定律二补齐。
4. **桥只有一个出口**。任何新的 JS↔宿主通信都必须复用 `_app_host_.invoke` / `registerHostMethod`，不得新开通道。
5. **事件构建期绑定**。禁止运行时树形状启发、禁止按事件名运行时分发。
6. **能力扩展走注册表**。新增运行时能力：JS 片段经 `JsUiLibrary.jsFragments` 注入、宿主 widget 经 `JsWidgetRegistry` 注册、桥接经 `ensureJsUiCapabilities` 就位——核心文件（runtime_source / reconciler / JsUiWidget / 生成器内核）零改动。若新能力还引入新的编译期组件类型，仍需按第 5 节登记 `js_widget_defs.dart` 的产物形态表。
7. **核心机制单点实现**。同一能力只在翻译层或运行时层的一处实现，组件与普通类同时生效；禁止为不同入口复制第二份逻辑。
8. **生命周期单入口**。页面资源释放只走 `disposeRoot`；JS 组件生命周期只由 mini-react 派发。
9. **宁可改业务，不改基座**。当业务写法与基座冲突时，优先调整业务写法；确需动基座时，先更新本文档再动代码。

## 5. 扩展指引（正确的加法姿势）

| 需求 | 应该改哪里 | 不应该改哪里 |
|---|---|---|
| 支持一个新的 Flutter widget 翻译 | 翻译路径本身无需 per-widget 代码（统一翻译直接覆盖）；但生成器需同步 `js_widget_defs.dart` 的 `builtinWidgetTypes`，有位置实参的登记 `widgetPositionalArgNames`，产物形态不同时再调 `builderFormTypes`；宿主 `JsWidgetRegistry`（或能力域 `capabilities/*`）注册 type → renderer（两端对称） | mini-react、JsUiWidget、组件业务代码 |
| 新增带 `.builder` / `.separated` 的滚动容器 | `js_widget_defs.dart` 的 `builderFormTypes` 登记类型（生成代理类） + 宿主 renderer 按 `children.__items` / `itemCount` 还原原生构造 | 运行时类型白名单（已不存在）、mini-react 核心 |
| 注册业务自定义数据载体（导航项 / 下拉项等） | 启动时 `registerJsDataCarrierType('MyItem')` | 生成器、翻译层 |
| 新增一个宿主能力（如新的 Controller） | `capabilities/` 新建能力目录：JS 片段 + Dart 桥 + kind 描述符，经 `JsUiLibrary` 注册 | runtime_source 骨架、句柄注册表核心 |
| 接入一个三方状态管理库 | 运行时：新建 `JsUiLibrary` 子类实现 `jsFragments`/`ensureChannels`/`registerWidgets` 三钩子并注册；编译期：`js_widget_defs.dart` 的 `logicWidgetTypes` / `widgetPackages` 登记，`widget_module_builder.dart` 的 `logicWidgetSources` 写 JS 类；若库有专属 BuildContext 扩展（如 `watch/read`），再经 `registerContextOp` 注册宿主处理 | hot_patch 核心代码、provider 已有实现 |
| JS 缺一个 Dart 标准库方法 | `runtime_source.dart`【1c】节向内建原型补齐同名同义方法（`defineProperty` + `enumerable:false` + 存在性守卫） | 生成器方法名映射、Dart 业务写法 |
| 新增一个纯原生组件 | `example/lib/main.dart` 中 `registerNativeComponent(name, build)` 全局注册一次 | 生成器、JS 运行时 |
