Guide · 自定义组件

组件树里的每一种组件，都有明确的落点

内建、自定义、三方组件全部走同一条翻译路径。大多数情况下你不需要写任何额外代码；只有组件需要宿主真值，或本身没有可翻译的 JS 实现时，才需要注册宿主侧实现。

先判断属于哪一类

组件的情况做法要改产物吗
注解组件的 build 里使用其他注解组件 / 本文件私有组件 生成器自动收集并翻译，运行时直接 new 自动
组件逻辑复杂、含原生依赖，不适合翻译 标 @PatchIgnore(isComponent: true)，再用 jsWidgetRegistry.register 注册宿主实现 重新生成一次
纯原生组件 / 跨库不可见的私有类 产物保留具体类型名，运行时按类型名查注册表 自动
业务 / 三方库的视觉组件，需要 JS 侧包装类 lib/custom/ 继承 JsUiLibrary 注册 + 根目录 js/<package>.js 写 JS 类 重新生成一次
i

判断依据不是类名，而是组件来自哪个文件、是否有对应的 JS 产物。所有类（包括 widget）都是普通类，框架不会按名字猜测「这是不是组件」。

i

命名约定：框架自有的公开类统一用 Js 前缀（JsUiLibrary、JsRenderContext、JsLog），全局入口用小驼峰 js 前缀（jsWidgetRegistry）。被翻译的组件、值类与三方库类不适用此前缀——它们必须与 Dart 源码同名。

嵌套与私有组件（自动）

被 @PatchEntry 标记的组件，其 build 树里引用的其它组件默认都会连带翻译：

  • 其他注解组件：生成 JS import，运行时递归加载；元素 type 是组件类引用 + import 相对路径。
  • 本文件私有组件（_LabeledDivider 等）：依赖分析自动纳入翻译，生成同名 JS 类注册进同一产物。
  • 同文件的公共组件：同样自动连带翻译。
  • 跨文件且无注解的公共组件：不会被连带翻译；产物保留其具体类型名，运行时走宿主注册。希望它有 JS 版本时，给它加 @PatchEntry。

使用方无需声明依赖，也无需为每个子组件单独配置：

@PatchEntry('DashboardCard')
class DashboardCard extends StatelessWidget {
  @override
  Widget build(BuildContext context) => Column(
        children: [
          const BannerCard(),           // 另一个 @PatchEntry 组件：JS import
          _SectionTitle('统计'),         // 私有组件：自动连带翻译
          const MetricRow(),            // 同文件公共组件：自动连带翻译
        ],
      );
}
i

只有当组件退出翻译（@PatchIgnore）或跨库不可见时，才需要宿主注册。注册是按类型名查找的，不影响其它组件的自动翻译。

纯原生组件注册

当某个组件不适合翻译、或需要在 JS 热更树里渲染一个纯原生实现时，用 jsWidgetRegistry.register 按类型名注册一次：

import 'package:flutter/material.dart';
import 'package:dynamic_flutter/dynamic_flutter.dart';

void registerAllNativeComponent() {
  jsWidgetRegistry.register(
    '_LabeledDivider',
    (c) => LabeledDivider(
      text: c.str('text') ?? '',
      child: c.children['child'] as Widget?,
    ),
  );
}

void main() {
  WidgetsFlutterBinding.ensureInitialized();
  registerAllNativeComponent();   // runApp 之前，全局注册一次
  runApp(const MyApp());
}

回调参数 JsRenderContext

成员说明
type产物里的元素 type（组件类型名）
props普通值 props；widget 已从 props 中拆出
children按 Dart 实参原名索引的槽位：单个 widget 是 Widget?，数组是 List<Widget>，数据载体数组是 List<JsRenderContext>
keyJS 侧声明的 key 对应的宿主 Key 实例；应原样传给真实 widget（key: c.key）
context本结点所在位置的 BuildContext（需要按位置取祖先时使用）
invoke(handler, args)把事件句柄回传到 JS 侧执行
on / on1 / on2 / on3 / on4把 props 上的事件句柄绑成 0～4 参的 Flutter 回调
str / num_ / int_ / double_ / bool_ / map按类型读取 props 并转换，缺失返回 null
element / elementList把值对象里的 Widget 字段就地还原成 widget（不进 reconciler 树）
!

注册是进程内一张全局表：在 runApp 之前注册一次即可，不要放进 build()。重复注册同名会覆盖并告警。

未注册时的行为是可见且可补救的：产物保留具体类型名（不降级为统一的 Component），debug 下渲染可见占位并上报 error，release 下为零尺寸。后续补注册同一份产物无需重新生成。

自定义视觉组件（带 JS）

如果组件需要出现在 JS 逻辑树里，且宿主侧有真实实现（三方包或业务组件），按下面三块接入。以示例工程里的 VisibilityDetector 为例，dynamic_flutter 包零改动。

1. JS 包装类：工程根 js/<package>.js

文件名即 Dart 包名。类继承 Component，构造即宿主结点；只有需要跨桥换成句柄的函数形参才列进 __fnProps，其余 props 原样下发。

// js/visibility_detector.js
import { Component } from '../flutter.js';

export class VisibilityDetector extends Component {
  static __fnProps = ["onVisibilityChanged"];
}

2. 宿主桥接：注册 type → Flutter widget

// example/lib/custom/visibility_detector/custom_visibility_detector_bridge.dart
void registerVisibilityDetectorWidgets(JsWidgetRegistry r) {
  r.register('VisibilityDetector', (c) {
    final handler = c.props['onVisibilityChanged'];
    return VisibilityDetector(
      // 用 c.key 取宿主 Key 实例，不要自己再造一把
      key: c.key ?? const ValueKey<String>('js.visibilityDetector'),
      onVisibilityChanged: handler == null
          ? null
          : (info) => c.invoke(handler, [
                {
                  'visibleFraction': info.visibleFraction,
                  'size': {
                    'width': info.size.width,
                    'height': info.size.height,
                  },
                }
              ]),
      child: (c.children['child'] as Widget?) ?? const SizedBox.shrink(),
    );
  });
}

桥接的职责边界：把 JS props 映射成真实 widget 构造参数；把宿主才能真正算出的事实编码成 JSON 回传。业务逻辑仍留在 JS。

3. 能力声明与注册

// lib/custom/visibility_detector/custom_visibility_detector_library.dart
class CustomVisibilityDetectorLibrary extends JsUiLibrary {
  const CustomVisibilityDetectorLibrary();

  @override
  String get id => 'visibility_detector';

  @override
  void registerWidgets(JsWidgetRegistry r) =>
      registerVisibilityDetectorWidgets(r);
}

// main()：runApp 之前注册
registerJsUiLibrary(const CustomVisibilityDetectorLibrary());

生成器构建期会扫描工程 lib/** 里的 r.register('X', …)，把 X 补进 flutter.js 的宿主包装类清单——与内建能力同一份清单，业务无需改 build.yaml。

i

如果组件还需要 Controller 句柄或可等待事件，在同一个 JsUiLibrary 的 ensureChannels() 里登记控制器桥；异步事件的「等结果」走通用 JsRuntimeManager.invokeAwait，不要新开跨语言通道。完整示例见 example/lib/custom/easy_refresh/。

@PatchIgnore

用于让某个组件退出翻译，热更时始终使用原生实现：

@PatchIgnore(isComponent: true)
class _LabeledDivider extends StatelessWidget {
  const _LabeledDivider({required this.text, this.child});
  final String text;
  final Widget? child;
  // …
}
用法行为
@PatchIgnore(isComponent: true)不翻译该类，但在声明它的源文件产物里生成同名包装类；使用方照常 new 类名({...})，运行时按 jsWidgetRegistry.register 渲染
@PatchIgnore()（默认）整类忽略：不翻译、不生成任何类；引用它的结点直接丢弃，并输出构建期告警

适用场景：组件逻辑复杂、含原生依赖，不适合翻译成 JS；或临时下线某个嵌套组件的 JS 版本。注解只是构建期元数据，不影响组件正常运行。

自检清单

  • 组件是否真的需要宿主实现？先确认它没有自动翻译产物。
  • 纯原生注册是否放在 runApp 之前、且不在 build() 里重复调用？
  • 注册的 type 是否与产物里的具体类型名完全一致（含下划线前缀）？
  • children 是否按 Dart 实参原名取，而不是假设固定叫 child？
  • 宿主 key 是否用了 c.key，而不是新建实例？
  • 改了宿主桥接或 JS 类后，是否重跑 build_runner 并重进页面验证？
